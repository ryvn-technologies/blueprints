# PostgreSQL Cloud SQL module

Provisions a Cloud SQL PostgreSQL instance with encrypted connections, automated backups, optional high availability, and optional IAM database authentication.

## Usage

```hcl
module "postgres" {
  source = "./infra/ryvn-postgres/gcp"

  project_id        = var.project_id
  region            = "us-central1"
  name_prefix       = "postgres"
  environment       = "production"
  private_network   = var.private_network
  database_name     = "app"
  database_password = var.database_password
}
```

Enable `sqladmin.googleapis.com` before using the module. Private networking requires an existing VPC with Private Services Access configured. For public access, set `publicly_accessible = true` and configure `allowed_cidr_blocks` for direct database connections.

The default administrator is `postgres`. Supplying `database_password` sets its password. Setting `database_username` to another name requests a built-in application user and requires a nonempty password, even when IAM is enabled. To omit password credentials, enable IAM and keep the default `postgres` username. All input options are documented in [variables.tf](variables.tf).

## Advanced IAM authentication

Set `iam_database_authentication_enabled = true` to enable `cloudsql.iam_authentication`. The module preserves the existing pg_cron flags. If you also supply a password, both authentication methods remain available through their separate database accounts.

`iam_database_users` registers existing Google identities as database accounts. The caller creates the Google identities, grants IAM access, configures workload identity, and assigns SQL privileges. The Postgres blueprint and user-provisioning job continue using their existing password configuration.

| Input | Default | Meaning |
| --- | --- | --- |
| `database_username` | `postgres` | Built-in password username; a custom name requests an application user and requires a password |
| `database_password` | `null` | Optional built-in account password; required when IAM is disabled or a custom password username is configured |
| `iam_database_authentication_enabled` | `false` | Enable IAM database logins, with or without password credentials |
| `iam_database_users` | `{}` | Map of stable labels to `{ email, type }` for accounts to register |

### Omit password credentials

For a new instance using IAM, omit `database_username` and `database_password`, or explicitly use their defaults:

```hcl
iam_database_authentication_enabled = true
database_username                   = "postgres"
database_password                   = null
```

On a new instance, Cloud SQL creates `postgres` without a password, so it cannot authenticate using a password. With the default username, the module creates no separate built-in application user, and the `username`, `password`, and `connection_string` outputs are null. Declare IAM identities in `iam_database_users` and use their metadata and `connection_name` for IAM connections. See [Cloud SQL's default PostgreSQL user](https://cloud.google.com/sql/docs/postgres/users#default_postgresql_users).

IAM account registration does not grant SQL privileges or create an IAM database administrator. Before relying on a deployment without password credentials, arrange administrator access and SQL grants through your own database administration process. The module's Google 6.x provider cannot assign database roles during IAM user creation.

Omitting a password is not an instance-wide ban on password authentication. For an existing instance with a custom password username, reset `database_username` to `postgres` before or alongside removing `database_password`. Resetting the username plans deletion of the module's separate built-in application user. Reassign its owned objects and clean up privileges before deletion. Do not rely on removing `root_password` from Terraform to revoke an existing `postgres` password; explicitly disable or revoke that login through your database administration process and verify it can no longer authenticate. Other accounts created outside the module are unaffected. Review the migration plan and verify IAM administrator access first.

The configured username determines whether the module creates an application user. Passwords generated by another resource during the same apply work with both IAM and password-only configurations; the password value does not determine the resource count.

### IAM account types

| Account type | Input email | SQL username |
| --- | --- | --- |
| `CLOUD_IAM_USER` | `operator@example.com` | `operator@example.com` |
| `CLOUD_IAM_SERVICE_ACCOUNT` | `app-runtime@my-project.iam.gserviceaccount.com` | `app-runtime@my-project.iam` |
| `CLOUD_IAM_GROUP` | `readers@example.com` | `readers@example.com`, used for group grants |

Emails must be lowercase and SQL usernames must fit PostgreSQL's 63-character limit. Only service-account emails lose the trailing `.gserviceaccount.com`. IAM accounts must have distinct SQL usernames and cannot share the configured built-in application user's name. Map keys identify Terraform resources; retain them when editing an account's configuration.

You can enable IAM with an empty user map to manage accounts elsewhere. A nonempty map requires IAM to be enabled. Cloud SQL creates group-member accounts automatically; do not declare `CLOUD_IAM_GROUP_USER` or `CLOUD_IAM_GROUP_SERVICE_ACCOUNT` entries. Group members log in with their own identities. An identity already registered individually must be removed before it can use group authentication on that instance, and membership changes take time to propagate. See [Google's IAM account documentation](https://cloud.google.com/sql/docs/postgres/add-manage-iam-users).

### Register an existing service account

Add these arguments to the module call. `var.application_service_account_email` is the full email returned by your identity manager:

```hcl
iam_database_authentication_enabled = true
iam_database_users = {
  app = {
    email = var.application_service_account_email
    type  = "CLOUD_IAM_SERVICE_ACCOUNT"
  }
}
```

The `app` key is a label, not a permission level. Registering the account does not grant read, write, monitoring, or administrator privileges.

### Grant Google IAM access

In the caller's Terraform configuration, grant the registered principal permission to log in. Proxy and connector users also need the client role. These resources manage individual members and preserve other project IAM bindings:

```hcl
resource "google_project_iam_member" "app_database" {
  for_each = toset([
    "roles/cloudsql.instanceUser",
    "roles/cloudsql.client",
  ])

  project = module.postgres.project_id
  role    = each.value
  member  = module.postgres.iam_database_users["app"].member

  condition {
    title      = "database-${module.postgres.name}"
    expression = "resource.name == '${module.postgres.instance_resource_name}' && resource.service == 'sqladmin.googleapis.com'"
  }
}
```

`roles/cloudsql.instanceUser` authorizes IAM login. `roles/cloudsql.client` authorizes proxy or connector connections; direct IP connections do not require that role. These IAM roles do not grant SQL table access. The example requests access for the named instance using Google's [resource-name condition](https://cloud.google.com/sql/docs/postgres/iam-conditions). Google's example covers the client permission; verify the separate database-login permission with the cross-instance checks below before relying on login isolation. An existing broader IAM grant still applies.

The identity applying the module needs Cloud SQL instance and user management permissions. Creating the caller-owned project bindings additionally needs `resourcemanager.projects.getIamPolicy` and `resourcemanager.projects.setIamPolicy`. If `managed_tag_value` is supplied, IAM database accounts are registered only after the tag binding, matching the existing application-user ordering. The module waits `managed_tag_propagation_wait` (90 seconds by default) after creating or changing that binding so its conditional IAM grant can propagate. This module does not enable project APIs or change project IAM policies.

### Connect a Kubernetes workload

For a Kubernetes ServiceAccount `production/app`, configure your identity manager to grant `roles/iam.workloadIdentityUser` on the Google service account to:

```text
serviceAccount:CLUSTER_PROJECT_ID.svc.id.goog[production/app]
```

Annotate the Kubernetes ServiceAccount with the Google service account's full email. For Ryvn's web-server chart:

```yaml
serviceAccount:
  annotations:
    iam.gke.io/gcp-service-account: app-runtime@my-project.iam.gserviceaccount.com
```

The pod must run as that Kubernetes ServiceAccount. A pre-deploy job uses `app-pre-deploy` and needs its own workload identity binding if it also connects to the database. The existing GCP workload-access module supports bucket grants only; configure these Cloud SQL associations in the caller's identity setup. See [Google's GKE connection guide](https://cloud.google.com/sql/docs/postgres/connect-kubernetes-engine#workload-identity).

### Assign SQL privileges

Connect as an established database administrator, using IAM or a password, and grant the IAM login membership in an application role with the required database, schema, table, sequence, and default privileges. For an existing role:

```sql
GRANT app_read_write TO "app-runtime@my-project.iam";
```

Use the SQL username from `iam_database_users["app"].username`, quoting email-shaped identifiers. A group account can receive SQL grants and pass them to its members. This module does not grant `cloudsqlsuperuser` to IAM accounts. The caller can manage custom roles and grants through SQL migrations or the PostgreSQL Terraform provider.

The module retains Google provider `~> 6.0`. That provider version does not support `google_sql_user.database_roles`; examples using the newer field require a provider upgrade. See [database privileges](https://cloud.google.com/sql/docs/postgres/add-manage-iam-users#granting_database_privileges) and the [6.x user resource](https://github.com/hashicorp/terraform-provider-google/blob/v6.50.0/website/docs/r/sql_user.html.markdown).

### Authenticate database connections

Use Cloud SQL Auth Proxy with `--auto-iam-authn`, or a language connector with automatic IAM authentication enabled. The proxy or connector must authenticate as the same Google identity as the requested SQL login. For a private-IP instance, run the proxy from a network that can reach it:

```sh
cloud-sql-proxy --auto-iam-authn --private-ip PROJECT:REGION:INSTANCE
psql 'host=127.0.0.1 port=5432 dbname=app user=app-runtime@my-project.iam sslmode=disable'
```

Use the `connection_name` output for `PROJECT:REGION:INSTANCE`. The local proxy connection above is unencrypted; run the proxy alongside the client and keep its listener on localhost. The proxy encrypts its connection to Cloud SQL. Network reachability is still required.

For manual authentication, obtain a fresh token with `gcloud sql generate-login-token` as the intended identity and pass it as the password over TLS. Tokens expire after one hour, so new physical connections need a valid token. Automatic connectors handle token refresh. When a password is supplied, the `password` and `connection_string` outputs contain credentials for the built-in account; they do not authenticate IAM users. Keep tokens out of Terraform state and durable connection configuration. See [Google's IAM login instructions](https://cloud.google.com/sql/docs/postgres/iam-logins).

### Remove accounts or disable IAM

Move clients to their replacement credentials and verify administrator access before removing IAM access. If disabling IAM entirely, first supply `database_password`, apply, and verify password administrator access. Reassign owned SQL objects and remove grants or memberships as needed before deleting an IAM account; Cloud SQL can reject deletion while dependencies remain. The module uses real account deletion, not `ABANDON`. Do not blindly run `DROP OWNED`, which can delete application objects.

Remove the entry from `iam_database_users` and apply to delete the database account. Remove its caller-owned IAM bindings as well. Changing an account's email or type also replaces its SQL user; renaming a map key changes its Terraform address and requires a state move to preserve the resource. To disable IAM entirely, remove managed IAM users first, then set `iam_database_authentication_enabled = false`. Accounts managed elsewhere lose IAM login access when the flag is disabled. The built-in password accounts remain available.

## Outputs

| Output | Meaning |
| --- | --- |
| `iam_database_users` | Map matching the input keys, containing `username`, `email`, `member`, and `type`; `{}` when no accounts are managed |
| `project_id` | Project containing the instance, for caller-owned IAM bindings |
| `instance_resource_name` | `projects/PROJECT/instances/INSTANCE`, for IAM conditions |
| `connection_name` | `PROJECT:REGION:INSTANCE`, for the proxy and connectors |
| `name`, `id` | Generated instance name and self-link |
| `host`, `endpoint`, `port` | Direct database connection address; private IP preferred |
| `private_ip_address`, `public_ip_address` | Individual connection addresses |
| `database_name` | Requested application database name, or null |
| `username`, `password`, `connection_string` | Built-in password credentials, all null when no password is supplied; password and connection string are sensitive |

## Validation

Run from this directory with Terraform 1.7 or later:

```sh
terraform fmt -check -recursive
terraform init -backend=false
terraform validate
terraform test
```

The tests use mock providers and make no Google Cloud calls. They cover supplied, omitted, and null passwords; credential outputs; IAM and pg_cron flag composition; account naming; invalid inputs; and changes between authentication configurations. They verify Terraform's configuration and planned resources, not live login revocation.

The caller fixture checks that a custom application user can be planned with a password generated during the same apply, both with and without IAM:

```sh
terraform -chdir=tests/fixtures/generated_password init -backend=false
GOOGLE_OAUTH_ACCESS_TOKEN=terraform-test-placeholder \
  terraform -chdir=tests/fixtures/generated_password test
```

The placeholder token satisfies the child module's embedded Google provider configuration. Every Google resource is overridden and the random provider is mocked, so this test does not authenticate to or call Google Cloud.

Before deploying this configuration to production, verify against disposable instances:

- Password login still works, and the registered IAM user can log in.
- With no password supplied on a new instance, `postgres` cannot authenticate with a password, no password application user exists, and an IAM account can log in with its separately configured SQL privileges.
- SQL queries fail without the intended grants and succeed after the grants.
- Proxy and direct IAM login succeed on the allowed instance and fail on another instance with the same IAM user registered. Test direct login separately so the client-role condition cannot hide a broader login grant.
- A principal without IAM login permission is denied, and automatic authentication reconnects after token expiry.
- Groups refresh without plan drift, and accounts can be removed after SQL ownership and privilege cleanup.

These live authentication checks have not been performed by the mock test suite.
